# Direct call media and floating panel

Real direct calls use the existing authenticated Socket.IO client through its `calls` channel. `DirectCallsRuntime` is mounted above account/voice navigation and exposes `useDirectCalls()` to real conversation headers. Supply `YahooChatWindow.callPeerId` from the owning conversation API (or a `ConversationHeader.callTarget`) inside that runtime. Demo Messenger retains explicit UI previews. No real contact list or recipient identities are fabricated; production conversation/identity adapters remain missing in this checkout.

`useLiveDirectCalls` coordinates the server invitation state and reuses `LiveKitConnectionService` and `useLiveRoomMedia` from Voice Rooms for capture, publications, audio playback, reconnection, device errors and teardown. Acceptance opens media only on the endpoints that explicitly placed/accepted the call. Connected status and duration start only after the expected peer is actually present in the connected LiveKit room. Other devices can observe signaling without automatically capturing media.

The authenticated `POST /api/calls/token` accepts exactly `{ callId, connectionId }`. It uses the same cookie, Origin, CSRF and session checks as the existing voice token endpoint, then calls `RealtimeServerHandle.authorizeCallMedia`. The socket ID is untrusted input: it must belong to that authenticated user/session and be the exact endpoint that initiated or first accepted this call. A second device receives `409 media_in_use`, without ending the owning device's call. Only accepted, currently authorized calls can mint tokens.

To integrate in the owning API host, construct `LiveKitConfig`, then inject `createDirectCallMediaLifecycle(config)` as `directCalls.media` alongside the real direct-conversation resolver when calling `attachRealtimeServer`. Pass that returned handle as `directCalls` to `createLiveKitHttpHandler`, with the real session resolver, authorizer, allowed origins and session-bound CSRF verifier. Keep the HTTP handler mounted before JSON parsing, as for `/api/voice/token`. Exported types/helpers live at `secubuzz-realtime-server/calls` and `/livekit`. The standalone host remains unavailable because those identity services are absent. Environment flags alone cannot enable calls.

Each invitation gets a distinct opaque private room, capped at two participants, with deterministic opaque identities for its two users. Direct-call tokens last at most 30 seconds and the remaining session lifetime. They permit only microphone, camera and screen video publication plus subscription, with no data publishing or administrative grants. The camera button can upgrade a voice call by enabling that user's camera; it never enables the peer's camera. Screen sharing uses `setScreenShareEnabled` on the same local participant with screen audio disabled. The browser chooser always requires an explicit user action; cancellation leaves voice connected. Browser Stop Sharing updates SDK publication state, and pending grants after hangup are stopped.

The floating panel is nonmodal. Minimizing/expanding changes presentation only, leaving the call controller and single audio renderer mounted at workspace scope. It retains duration, status, actual participant names and device/hangup controls. Stop Sharing remains available while minimized. Local and remote screen tracks use the existing muted `VoiceVideo` renderer without mirroring. Camera tiles reuse Voice Rooms tiles. No second connection is created for screen sharing or minimizing.

Terminal signaling, media errors, endpoint/session loss, access revocation and unmount release local capture and remote attachments. The server's media lifecycle deletes the room, retries deletion failures, and also deletes a room that finishes creating after hangup. New token requests for ended calls are denied. Existing deployment-specific token revocation limits still apply: room deletion disconnects current participants; self-hosted deployments must account for already-issued/refreshed tokens when enforcing strict rejoin revocation. See [LiveKit token lifecycle](https://docs.livekit.io/frontends/reference/tokens-grants/) and [room management](https://docs.livekit.io/intro/basics/rooms-participants-tracks/rooms/).

Automated tests exercise real Socket.IO/authenticated HTTP boundaries and signed tokens with a test room-management SDK, and two frontend controllers with SDK track/event fixtures. Actual two-browser LiveKit/TURN, device-picker and mobile browser verification still requires the production identity/conversation/CSRF adapters and a configured LiveKit host. No database schema or security implementation is changed.
