# DB-4A integration contract — conversations only

DB-4A extends the existing injected `createRepositories(db).conversations` and `members` namespaces. It creates no separate store or competing conversation schema. [OpenAPI](conversations-openapi.json) is the machine-readable HTTP contract. [Handoff](db4a-handoff.md) records scope and verification.

## REST interface

| Method / endpoint | Input | Success |
| --- | --- | --- |
| `GET /api/conversations` | Optional `limit` (default 20, 1–50), opaque `cursor` | 200 `{items: Conversation[], nextCursor: string|null}` |
| `POST /api/conversations/dm` | Exactly `{recipientId: string}`; owner comes from session | 201 `{conversation}` for new creation; 200 `{conversation}` for existing/activated legacy DM |
| `GET /api/conversations/:id` | Opaque conversation ID; no query parameters | 200 `{conversation}` |

Example request body:

```json
{"recipientId":"22222222-2222-4222-8222-222222222222"}
```

Example success (no messages/previews/private profile fields):

```json
{
  "conversation": {
    "id": "33333333-3333-4333-8333-333333333333",
    "type": "direct",
    "participants": [
      {"id":"11111111-1111-4111-8111-111111111111","username":"alice","displayName":"Alice","avatar":"initials"},
      {"id":"22222222-2222-4222-8222-222222222222","username":"bob","displayName":"Bob","avatar":"star"}
    ],
    "createdAt":"2026-11-14T12:00:00.000Z",
    "updatedAt":"2026-11-14T12:00:00.000Z",
    "interactionAllowed":true
  }
}
```

Participant order follows the canonical binary user-ID pair and is the same for both callers; it is not actor-first. New IDs are UUIDs generated by the existing DAL. IDs are opaque and immutable. Explicitly approved legacy DMs retain DB-1's IDs (which can exceed the social identifier limit); conversation identifiers support 1–1024 ASCII identifier characters. Recipient IDs retain DB-3's 1–128 limit. Consumers must not derive a conversation ID, use the recipient ID as the conversation ID, or assume every existing ID has UUID syntax.

## Session, CSRF, Origin and errors

Use DB-2's existing same-origin HttpOnly cookie. Before every POST, bootstrap `/api/auth/csrf` and send `X-CSRF-Token` with browser-managed Cookie/Origin. Do not put owner/sender/session IDs into the body, URL query or headers. Unknown fields and query filters are rejected. Mutations require JSON (8 KiB maximum); no raw legacy CRUD route is opened. Repeating a user-requested POST is idempotent by pair, but clients should still reconcile uncertain results rather than automatically retrying arbitrary future writes.

Errors remain `{code,fields}`:

| Status / code | Meaning |
| --- | --- |
| 400 `VALIDATION_ERROR` | Invalid body, recipient/self, identifier, cursor, limit, duplicate/owner-selecting parameters |
| 401 `UNAUTHENTICATED` / `SESSION_EXPIRED` | Missing/revoked/expired session or disabled/noncredential account |
| 403 `CSRF_INVALID` / `FORBIDDEN` | Invalid proof/transport/Origin, or no confirmed friendship for initial creation/legacy activation |
| 404 `NOT_FOUND` | Unknown, unrelated, blocked, inactive, archived, unsupported group, or incomplete/left-membership conversation; no distinction is exposed |
| 409 `CONFLICT` | A trusted competing persistence operation violated a uniqueness contract; normal concurrent API calls return the existing ID |
| 413 / 415 | Oversized or unsupported body/encoding |
| 429 `RATE_LIMITED` | Shared SQLite rate bucket; numeric `Retry-After` seconds |
| 500 `INTERNAL_ERROR` | Sanitized unexpected persistence failure, with transaction rollback |
| 503 `SERVICE_UNAVAILABLE` | Bounded busy/locked database; no partial creation |

Responses inherit DB-2's no-store and security headers. Raw SQL, cookies, proofs, hashes, private email/status/preferences and plaintext previews are never returned or logged. Limits are 120 reads/minute/actor and 60 mutations/minute/actor plus 120 mutations/minute/source; forwarded IP headers do not replace the direct peer.

## Membership and relationship policy

- Both participants must be current active credential-enabled accounts, have active pair memberships and an unarchived direct conversation.
- Initial creation requires a current `Friendships.origin='authenticated'` grant. Pending requests and legacy friendship projections do not qualify.
- Existing authenticated DM metadata stays readable after unfriend, with `interactionAllowed=false`. A POST for that existing pair is a lookup only: no second conversation, timestamp change, implicit friendship, notification or new audit event.
- Either-direction block hides the conversation from both lists and returns the same 404 for detail/create-or-retrieve. The physical row, memberships and existing ciphertext remain intact.
- Unblock can restore metadata visibility, but does not restore friendship or permission for future interactions. Disabled accounts, left/missing members and archives are not revived through POST.
- Existing `origin='legacy'` conversations stay hidden. An explicit, unblocked, friendship-approved POST may activate an intact legacy pair in place. It preserves stable ID, original creation time, members and ciphertext; activation updates provenance/updated time and safe audit metadata in the same transaction. It does not approve old ciphertext as modern message history.
- `interactionAllowed` describes current policy only. It cannot authorize a later message write.

## Pagination

Lists use `updated_at DESC, conversation_id DESC`, a strict lexicographic keyset, `limit+1` bounded SQL and a single joined participant projection. No offset scan, global count or per-row participant queries are used. A returned cursor is bounded base64url JSON tied to actor and endpoint; malformed/noncanonical, cross-actor and owner-selecting inputs fail. Cursor contents are not credentials or authorization grants; every page reapplies membership, account and block restrictions.

These are current-state pages, not a frozen multi-request snapshot. Relationship changes can remove rows between pages; future DB-4B timestamp changes may reorder rows. Refresh from the first page after a mutation, and deduplicate client lists by opaque conversation ID. No synthetic last-message timestamp or message preview exists in DB-4A.

## Existing repository and service interfaces

`createRepositories(db)` still owns all SQL persistence. New/extended trusted internal methods:

| Method | Behavior |
| --- | --- |
| `conversations.create(input)` | Existing atomic conversation/member creation; optional internal `origin` field. Omission stays legacy, including compatibility with older migration versions. Not a public authorization boundary. |
| `conversations.createAuthenticatedDirect(actorId, recipientId)` | Canonicalizes the pair and delegates to the existing atomic create/member path. Caller must already hold the service authorization transaction. |
| `conversations.findDirect(a,b)` | Existing unique unordered-pair lookup, including legacy rows. |
| `conversations.activateDirect(id, at)` | Internal legacy provenance/update-time change; no identity or ciphertext rewrite. |
| `conversations.getDirectForUser(actorId,id)` | Current joined member/account/provenance/archive/block visibility and derived friendship hint. Internal rows are projected before HTTP output. |
| `conversations.listDirectForUser(actorId,{limit,after})` | Same visibility predicates, keyset order and at most limit+1 joined rows. |
| `members.get/list` | Existing scoped membership lookup; no competing membership repository. |

`createConversationService({db,auth,limiter?})`, exported by `application.conversations`, offers `createDirect`, `detail`, `list`, rate handling and shared authorization. It reuses DB-3's active-account/friendship/block helpers and DB-2's session/proof verifiers on the same connection. No authentication implementation is duplicated.

## DB-4B shared authorization boundary

Two interfaces are ready for future message work, without implementing it:

```js
// Existing REST proof plus the same authoritative interaction policy:
conversations.withInteraction(context, proof, conversationId, (capability, repositories) => {
  // DB-4B will perform its synchronous authorized message operation here.
  // No message-write operation is supplied by DB-4A.
});

// For an owning composition that already holds this connection's transaction:
const capability = conversations.authorizeInTransaction(context, conversationId, {interaction: true});
// {conversationId, type:'direct', participantIds:[low,high], recipientId, interactionAllowed}
```

`context` is the trusted `{userId,sessionId}` reference resolved through DB-2; `proof` is the verified session CSRF proof from middleware. Never construct either from untrusted sender fields. `withInteraction` opens BEGIN IMMEDIATE, rechecks the durable session and CSRF proof, checks both active members/accounts, archive, authenticated provenance, blocks and confirmed friendship, then invokes synchronous work on the existing repositories. A thrown error rolls the entire transaction back; async/Promise work is rejected. `authorizeInTransaction` refuses use without a transaction and repeats the same policy; message writers must use an immediate transaction and keep checks and persistence together, without awaits or connection changes.

Kiro must still supply its trusted resolver/transport contract before invoking this boundary; no socket wiring, resolver shortcut, CSRF bypass or cryptography is introduced here. A metadata GET, earlier socket handshake or cached `interactionAllowed` must never substitute for this write-time check. DB-4B must agree message ID scope, fingerprints, encrypted envelope validation, legacy-message access rules, idempotent writes and receipt semantics with the owning teams. Existing globally unique Message IDs and legacy ciphertext are unchanged.

## Deployment and frontend handoff

Apply pending migrations through the existing startup/CLI workflow with the intended persistent DB_PATH and normal backup policy; never reset the development database. Restart the DATA process after source changes so its in-memory module graph loads DB-4A. This task verifies isolated databases and does not restart or migrate the user's existing development database.

Frontend ownership must separately add same-origin mappings for the three documented conversation paths and a real conversation adapter. Current client rewrites stop at DB-3, so these APIs are not presented as wired into the UI. Realtime, groups, attachments, encryption and messages remain disconnected. Stop at DB-4A; DB-4B requires the user's separate approval.
