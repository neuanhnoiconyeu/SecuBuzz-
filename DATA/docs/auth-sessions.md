# DB-2 password, session and CSRF architecture

The backend uses [node-argon2](https://github.com/ranisalt/node-argon2) 0.45.2, pinned in the package/lockfile. Passwords use Argon2id v19, 19456 KiB (19 MiB), two iterations, one lane and a 32-byte hash. The library generates an independent random salt for each hash and stores the parameters/salt/hash in PHC format. These parameters meet the [OWASP password-storage minimum](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html). Benchmark and increase them for deployment capacity; there is no environment switch to reduce the work factor.

Unknown accounts perform dummy Argon2 verification instead of returning before password work. Public invalid-credential responses are identical for wrong/unknown/legacy/disabled accounts; this is not a statistical constant-time HTTP guarantee. At most two hash/verify operations run concurrently per process; excess work returns 429 instead of entering an unbounded queue. Verification accepts bounded stored costs (at most 256 MiB, ten iterations, four lanes). Malformed or excessive hash metadata is not executed as an unbounded KDF. Successful login upgrades weaker hashes and retains stronger hashes; upgrading a hash revokes older sessions through credential-version rotation. SQL transactions begin after asynchronous password work, then recheck credential/account/proof state before creating an account/session.

## Durable sessions

- Generate a fresh 32-byte cryptographically random bearer token for every successful login, encoded as canonical 43-character base64url. Separately generate the opaque internal session UUID. Never promote a pre-session or accept a client-selected session ID.
- Store only SHA-256 of the random bearer, its CSRF verifier, user ownership, issue/expiry metadata and `auth_version` in Sessions. Fast SHA-256 is appropriate here for random 256-bit token verifiers; it is never used alone for passwords.
- AccountCredentials holds private normalized email/username lookup keys, Argon2 hash, status and authentication version. Public Users/UserProfiles remain separate. Existing credential-less users are reserved legacy identities, not active accounts. There is no claim/default-password/recovery API. A later claim process requires independent ownership verification and its own security review.
- DB-1 sessions receive auth_version 0. Credential-enabled accounts begin at version 1, so an old foundation row cannot become valid after enrollment. Every resolution joins the real user/profile and active credential record, checks matching versions, expiry, revocation and reserved demo IDs. User IDs from request bodies/headers/query/JWTs are ignored as authority.
- Default lifetime is eight hours, fixed from issue time. Configurable range is five minutes through seven days. No sliding refresh or indefinite socket authentication.
- Logout revokes exactly the active browser's session in SQLite, clears both cookies and emits a metadata-only auth event. A subsequent replay is rejected, including by another process using the same database.
- Up to five live sessions are retained per account. New login replaces any authenticated browser session presented with its proper CSRF proof; other sessions remain until expiry, explicit revocation, cap eviction or account-security change. Revoked/expired records are not reused.
- Changing password_hash or account status increments credential version and revokes that account's sessions. Deleting the private credential record also invalidates resolution because the required join disappears. User deletion remains restricted by DB-1 references; no destructive account-delete workflow was added.

Production cookie: `__Host-secubuzz_session`; pre-session: `__Host-secubuzz_preauth`. Both are Secure, HttpOnly, SameSite=Lax, Path=/, host-only (no Domain). Session Max-Age matches the configured lifetime; pre-session lifetime is ten minutes. Explicit local HTTP development uses names without `__Host-` and omits Secure only when NODE_ENV is development/test, AUTH_ALLOW_HTTP_LOCAL=true, Origin is loopback and the peer is loopback. The production loader rejects this override. No raw bearer is returned in JSON, stored in SQLite, or logged.

## CSRF

Login CSRF requires proof before authentication. DB-2 follows the [pre-session and synchronizer-token approach](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html): GET `/api/auth/csrf` creates/reuses an anonymous ten-minute pre-session cookie and returns its proof. SQLite stores only nonce/proof hashes; successful guest registration/login/logout consumes the pre-session within the same transaction. Concurrent reuse is rejected.

For stable bootstrap across tabs and process restart, derive a 32-byte proof with HMAC-SHA-256 keyed by the random cookie token, over the versioned label `secubuzz:csrf:v1:preauth` or `secubuzz:csrf:v1:session`. Persist only SHA-256 of that proof. The returned proof cannot reconstruct the cookie key and is not accepted as a bearer. The session proof is stable until its session ends, while each newly issued session/pre-session gets an independent random key. No server-wide CSRF secret, raw-token persistence or per-fetch rotation race is required.

Before mutations, require exact allowlisted Origin and a timing-safe comparison against the appropriate stored proof verifier. A valid authenticated cookie always requires that session's proof; a guest proof cannot override it. Login/registration recheck proof validity after hashing and inside the account/session transaction, closing expiry/revocation/reuse races. Authenticated logout similarly rechecks before revocation. Session-bound proofs stop working after expiry, revocation, credential version change or logout. A fresh guest bootstrap allows a safe already-logged-out retry.

GET bootstrap disallows cross-site browser Fetch Metadata and unapproved Origin/Referer. Mutation Origin is always required. No wildcard or credentialed CORS support exists. CSRF is additional to SameSite, HttpOnly, TLS, same-origin routing and safe input/error handling; XSS in the trusted frontend remains outside this mechanism's protection.

## Storage maintenance

`npm run auth:cleanup` deletes expired challenges/rate windows and session records expired or revoked at least seven days earlier. It logs only aggregate counts. It never deletes users/messages/contacts. Schedule it against the same SQLite database from one operational job. Challenge issuance additionally prunes expired challenges and refuses new issuance at 10000 live challenges; live proofs are not evicted. Session lookup remains authoritative without cleanup; a purged expired row becomes generically unauthenticated instead of SESSION_EXPIRED.

Database backups, host access controls and encrypted disks remain operational responsibilities. A database read exposes private email and password/session verifiers, not raw bearer tokens or plaintext passwords. SQL access is privileged and is not itself protected by HTTP authentication.
